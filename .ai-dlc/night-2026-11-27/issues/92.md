## Title

Volume toaster on rocker steps for every screen except NowPlaying (ReTune
capture-22 parity)

## Body (verbatim)

_Requested by the maintainer during the PR #91 host device pass 2026-11-26._

### Requirement

Hardware volume rocker steps must go **only to the OwnTone server** (verified
true today on develop @ `251a8b2`: server-only, `volume_music` unchanged, PR
#91 comment row 3) **and** show a transient volume indicator:

- On **every screen except NowPlaying**: a floating volume bar/toaster above
  the UI, ReTune-parity per `docs/retune-capture/22-volume-toaster/notes.md`
  (machine-verified reference: custom Toast, center band y≈900–1500,
  auto-hides ~1–2.5 s, **no a11y node**, keys intercepted app-wide, step
  5/press).
- On **NowPlaying**: **no** toaster — the existing 0–100 volume slider IS the
  indicator and must move with each rocker step. (Slider-follows-volume
  already verified on device: SeekBar `content-desc` 40%→50% + 4062 px
  localized band diff, PR #91 comment.)

### Current state

No toaster/overlay exists anywhere in the app (`grep -rniE
"toaster|toast|overlay.*volume" lib` → only the contrast comment in
`lib/src/ui/mini_player.dart:21`). Device-verified today: rocking on the
restored-NowPlaying launch screen changes only the slider band (center toaster
band 0 px), and a ReTune control press in the same band yields 275,103 px —
so the pixel oracle for the acceptance row is already built (see PR #91
comment row 1 method).

### Acceptance

- [ ] Rocker up/down on a non-NP screen (debug build, server paused): server
  volume steps ±R-14 step **and** a transient bar appears in the center band
  (pixel-diff >0 in y900–1500 within 1 s of the press, back to baseline ≤3 s)
  with no `volume_music` change.
- [ ] Rocker on NowPlaying: no toaster (center band stays 0 px) and the
  volume slider moves with each press (existing behaviour pinned by a widget
  test citing this issue).
- [ ] Toaster is transient (auto-hide) and exposes no a11y node (parity with
  ReTune's Toast — ScreenReaders unaffected).
- [ ] Gates green; tests cite R-06/D20 + this issue.

## OpenHands AI triage (verbatim AC list — the build target)

### Scope
Add an app-local, transient volume level indicator driven by the existing #84
foreground rocker path (`MainActivity.onKeyDown -> VolumeKeys.onKeyEvent ->
owntone_remote/volume_keys -> MirrorAudioHandler.handleVolumeKey ->
PlayerController.stepVolume`). It shows on every route except the Now Playing
root route, where the existing 0-100 slider already IS the indicator; ReTune
capture-22 parity = center band (y~900-1500), auto-hide ~1-2.5 s, no a11y
node. The routing itself is out of scope: session stays published `fixed`,
server-only, volume_music untouched - device-verified on develop @ 251a8b2
(PR #91 rows 3 and 5). Everything below except the pixel/band observations is
buildable and verifiable in the sandbox (fakes + widget tests); the on-screen
capture rows are host-bound and get BLOCKED-PENDING-HOST-VERIFICATION rows in
the PR body plus a request for `needs-host-tools` - the pixel oracle and its
baselines (0 px ours vs 275,103 px for ReTune in the same band, 4,062 px for
the NP slider) already exist from PR #91 row 1.

### Non-goals
No change to the rocker-to-server mechanism, its foreground gates, or the
session's `fixed` volume control (#84 / R-06 / D20 stand as-is); no change to
the Now Playing slider, its drag-state handling, or its 0-100 semantics; no
toaster on Now Playing. No new dependency (no toast/overlay package) and no
port of ReTune's Android layout or assets - the level bar is rendered by this
app's own widget layer, the way MiniPlayer is its own layer. No new settings:
no toaster toggle, position, or opacity option, and no change to rocker.step
semantics or its 1-10 clamp. No change to the media-session notification,
SystemUI tile/output-row rendering, or the hold-to-repeat cadence question
left open in PR #91 row 6. Deliberately no accessibility label on the
indicator - ReTune's Toast has no a11y node, so this is parity, not an a11y
gap to fix.

### Acceptance Criteria

- [ ] **AC-1** Non-Now-Playing screen (debug build, server paused, app
  resumed): a rocker press issues `PUT /api/player/volume?step=±<rocker.step>`
  AND a level bar appears in the center band (changed pixels > 0 in
  y900-1500 within 1 s of the press) and is back to baseline within 3 s;
  `settings get system volume_music` is unchanged across the whole sequence.
  Host-bound: record as BLOCKED-PENDING-HOST-VERIFICATION in the PR body and
  request `needs-host-tools`; the pixel oracle and baseline (0 px ours vs
  275,103 px ReTune in the same band) are already built - PR #91 row 1.
- [ ] **AC-2** Now Playing (the root route, including the restored-NP launch
  screen): the same presses produce ZERO changed pixels in the center band
  and the 0-100 volume slider moves with each press (SeekBar content-desc
  tracks the new volume). Pin the no-toaster half with a widget test citing
  R-06/D20 and issue #92.
- [ ] **AC-3** The indicator is transient without user interaction (~1-2.5 s
  auto-hide) and a subsequent press while it is visible resets the timer and
  updates the level in place - a repeated or held sequence keeps exactly one
  bar showing the newest level, never a stack of them.
- [ ] **AC-4** The bar shows the level actually requested: the post-step,
  clamped 0-100 value the same optimistic update `PlayerController.stepVolume`
  applies - so it agrees with the NP slider for the same press - and it does
  NOT appear when no request was issued (not connected / offline, where
  `_action` returns without an API call). Offline presses stay visually inert,
  matching the mini bar's 'offline -> transport inert' rule.
- [ ] **AC-5** Coverage and layering: the bar appears on the Library/Search,
  Queue, Outputs and Settings routes (and the drawer destinations reached from
  them), rendering above list content as its own non-blocking layer - it must
  not consume taps meant for rows behind it and must coexist with the mini
  player and the offline banner.
- [ ] **AC-6** No a11y node: a semantics-tree test pumps a non-NP screen,
  fires a rocker step through the existing fakes, and asserts the overlay
  contributes no semantics node (parity with ReTune's Toast); the existing
  semantics tests for the screen below it are unaffected.
- [ ] **AC-7** Backgrounded / screen-off / service-only restart: unchanged
  from #84 - no server step AND no indicator scheduled. Extend the existing
  foreground-guard test (`test/rocker_foreground_test.dart`) with an
  assertion that a declined key (`handleVolumeKey` returns false) starts no
  timer and builds no overlay.
- [ ] **AC-8** Quality gates green per AGENTS.md: `flutter analyze` 0 issues,
  `dart format --set-exit-if-changed .` clean,
  `flutter test --exclude-tags live` green, `flutter build apk --debug`
  succeeds; the new tests and the PR body cite R-06/D20 and issue #92;
  `docs/SESSION-LOG.md` entry appended.
