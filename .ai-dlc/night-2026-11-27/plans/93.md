## INTENT

Cold boot (or any first-attempt failure) while the OwnTone server is
unreachable puts `ConnectionController` in `ConnectionPhase.error` and it
stays there until the user taps Retry: the recovery `Timer.periodic`
(`_offlineProbe`, connection_controller.dart:373) is armed only on entry to
`offline`, and no connectivity listener exists. Fix: re-drive the connect
attempt automatically while in `error` after a network-y failure, so
`error → connecting → connected` happens on its own when the server returns.

## APPROACH

All logic lives in the controller that owns the phase machine; nothing else
changes shape. Files:

1. **`lib/src/connection/connection_controller.dart`** (only lib change):
   - New field `Timer? _errorRetry` + new ctor param
     `Duration errorProbeInterval = kOfflineProbeInterval` (the issue's
     "same probe/retry timer" ⇒ same 10 s cadence as offline; separate
     injected field so tests run at 50 ms like the existing offline tests).
   - New private `bool _errorAutoRetry` = "the failure that took us into
     `error` was network-y". Set in the `on DioException` catch
     (connection_controller.dart:235–239) from `err.reason`:
     true for `{dns, refused, timeout}` (the reasons a black-holed
     network / down server / dead DNS produce — connection_error.dart
     maps unreachable/no-route to `refused`), false for
     `{unauthorized, http, other}` and for the generic `catch (e)` site
     (240–244). Cleared in the `connectTo` prologue (next to
     `_errorMessage = null`) and by `disconnect()`.
   - Arm/disarm in `_setPhase` (mirrors the offline arm, ~370–381):
     entering `error` AND `_errorAutoRetry` ⇒
     `_errorRetry ??= Timer.periodic(_errorProbeInterval, (_) { if
     (_phase == ConnectionPhase.error && _config != null) unawaited(retry()); });`
     Every other phase entry cancels **both** `_offlineProbe` (unchanged)
     and `_errorRetry`. Entering `offline` also cancels `_errorRetry`.
   - `_teardownClient()` (349–364) also cancels/nulls `_errorRetry`
     (covers `dispose()`).
   - Why `retry()` (→ `connectTo(_config)`) and **not** `_probeServer()`:
     in `error` the failed attempt already ran `_teardownClient()` —
     `_api`/`_dio` are null, so `_probeServer` no-ops (306). `retry()` is
     exactly the code path the host observation proved recovers
     (`conn.retry()` → `error → connecting → connected`), reuses the
     per-attempt `connectTimeout`/`receiveTimeout` budgets, and
     `_setPhase(connecting)` inside `connectTo` cancels the timer before
     the first await, so ticks can never overlap attempts (callback
     re-checks `_phase == error` anyway). The failure catch re-arms the
     timer → self-sustaining cycle at fixed 10 s, same feel as the
     offline probe (its doc comment justifies fixed-interval LAN probes).
   - Class doc state machine (+ test-nameable behaviour): add
     `error → connecting` edge "(automatic retry timer, network-y
     failures only — unit 3/#93)" and a field doc comment in the
     `_offlineProbe` style (delete-the-timer → issue-regression story).
2. **`lib/main.dart`**: **no change** (issue names it only as the
   connectivity-listener candidate site — rejected, see RISKS; the
   listener that starts the media session on first connect already fires
   for a timer-driven connect exactly as for a tap-driven one, and the
   startup `connectTo(saved)` path is untouched).
3. **No change** to `root_screen.dart`/any UI (AC-5), `connection_error.dart`
   (classification already exists and is used as-is), `ws_client.dart`,
   backoff, or `pubspec.yaml` (no new dependency — minimal interpretation
   of the issue's "and/or").

Out of scope (recorded, not fixed): `connectTo`'s success/failure
continuations still lack the `_generation` guard `_probeServer` has — a
stale attempt can stomp a newer one (pre-existing; only reachable via
connectTo-while-connecting, which the UI already prevents; untouched by
this fix since the error timer only fires when no attempt is in flight).

## RISKS

- **A-1 (assumption, minimal interpretation)**: the issue's "and/or"
  connectivity listener is **not** built — no `connectivity_plus`-class
  dependency exists in pubspec; a timer-only fix satisfies AC-2/AC-3 and
  keeps the file set minimal. A listener would additionally cover the
  process-deep-idle case; out of scope here (recovery delay is one probe
  interval).
- **A-2 (assumption)**: network-y = `{dns, refused, timeout}`.
  `http`/`badCertificate`/generic-`other` errors do not auto-retry (a
  server answering wrongly is not a network-recovery class; T5 pins no
  spin). If a reviewer argues `http` should retry, it is a one-line set
  extension, not a shape change.
- **A-3 (assumption)**: fixed 10 s cadence (reuse of `kOfflineProbeInterval`
  as the default) instead of exponential backoff — per the issue's "the
  same probe/retry timer" and the existing offline rationale
  (connection_controller.dart:49–56).
- **A-4 (assumption)**: `retry()` reuses the in-memory `_config`; the
  error-phase loop therefore retries the *same* host (settings changes go
  through `connectTo` directly and are unaffected).
- **A-5 (assumption)**: "repoint to server" (run config) is realized as
  D-2's wifi re-enable making the configured server reachable again — the
  in-memory config cannot be repointed without a UI tap, which would stop
  testing the timer. A blackhole host alone can never recover, so D-1
  evidences entry + cycle, D-2 evidences no-tap recovery (the issue's own
  observation was wifi off → on).
- **VERIFY-LIVE 1**: 192.0.2.1 on the night AVD yields a `timeout`-reason
  (dio `connectTimeout` 5 s) — builder confirms the logcat reason/mode and
  that the auto cycle starts; if the image short-circuits it to
  `unreachable` that is still `refused`-reason (eligible) — either is
  fine, but confirm it does NOT land as `other` (then the gate would
  wrongly exclude it).
- **VERIFY-LIVE 2**: wifi toggle command honoured on
  `android-36 google_apis` (`svc wifi disable` / `cmd wifi
  set-wifi-enabled disabled`) — verify via `adb shell` before relying on
  it; fallback if neither works: airplane mode via `cmd connectivity` or
  `settings put global airplane_mode_on` + broadcast, else record D-2 as
  BLOCKED with T1–T3 as substitute proof.
- **VERIFY-LIVE 3**: server reachability + pause invariant at device-pass
  time (verified 2026-11-27 by planner: `/api/config` 200, `/api/player`
  `state=pause`, `volume=46`, progress stable across reads). The other
  live session can move player state between reads — never "restore"
  anything; only assert the two invariant-1 checkpoint reads agree.
- **R-1**: `connectTo` continuations remain unguarded by `_generation`
  (pre-existing; class of bug only reachable via concurrent `connectTo`,
  which the error timer cannot create — argued in APPROACH). If the
  reviewer flags it, the fix is out of this issue's scope → follow-up
  issue, not scope-widen.
- **R-2**: the WS created by each successful attempt opens against the
  night AVD's network; during D-1 (blackhole) no WS is ever created
  (getConfig never succeeds), so no WS-side hang interferes with the
  error-phase cycle.
