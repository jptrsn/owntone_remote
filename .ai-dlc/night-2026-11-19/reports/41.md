options") carrying ReTune's four labelled entries — **Play All · Shuffle ·

**Empty-list rule (chosen minimal, adjudication-compliant):** while the
list has not loaded or `total == 0`, the WHOLE overflow button is
`enabled: false` — every entry would be a no-op; a stable disabled button
beats a menu of dead entries. Pinned by a widget test.

**Controller** (`QueueController`, all through the existing `_action` =
unit-011 single-flight + trailing-refresh pattern; WS `queue` events keep
refreshing):

- `addUris(uris, {ahead})` → `POST /api/queue/items/add` **without
  `clear`**, `playback=add`; `ahead: true` → `position=0` (Play Next,
  orchestrator-frozen); the tail case **pins `position` to the current
  queue length** (see live findings — an omitted position would insert at
  a RANDOM slot while the server's shuffle mode is on).
- `playUrisShuffled(uris)` — **client-side pre-shuffle** then the same
  replace-and-start contract as `playUris` (`clear=true&playback=start`).
  Code comments keep the distinction visible: **Play All = clear+start;
  Play Next/Add = no clear, playback=add**.

**API** (`OwntoneApi.addUris`): `POST /api/queue/items/add` with
`uris` comma-joined + `playback=add` (+ `position` only when given), no
`clear`, no `shuffle` param.

**Live verification of the add surface (29.3 server, 2026-11-20, all adds
WITHOUT playback=start, state re-verified `pause` before/after every
step, every added item deleted again by id):**

- `playback=add` accepted (200), player state never left `pause`.
- `position=0` lands the block at absolute positions 0,1 (verified with a
  2-track add inside the 1393-item queue).
- **The add-time `shuffle` param is the GLOBAL shuffle-mode setter**
  (docs + live: `shuffle=false` on an add flipped `/api/player`'s
  `shuffle` to `false`; restored to `true` via `PUT
  /api/player/shuffle?state=true`, verified byte-identical). It is NOT an
  "add these items shuffled" flag → **client-side pre-shuffle chosen** for
  Shuffle-play, per the spec's "if none usable without playback=start, do
  client-side pre-shuffle" clause.
- **Omitted or out-of-range `position` with server shuffle ON inserts at
  a RANDOM slot inside the unplayed region** (observed positions 640,
  597, 1061, 710, 1072 across six no-position adds into a ~1396-item
  queue; `position=999999` also scattered to 1072). An exact
  `position=<real count>` appends at the tail (verified `position=1393`
  → landed 1393). Hence the controller pins `position = _queue.length`
  for Add to Up Next.
- `limit=-1` on `/api/library/{albums,playlists}/{id}/tracks` returns the
  whole set in one request (verified live: album 15/15, playlists 13/13) —
  the Shuffle path expands the set to per-track URIs with ONE fetch
  (Play All / Play Next / Add ride the container URIs —
  `library:playlist:N` / `library:album:ID` / `library:artist:ID`, the
  server expands them in order).

## ASSUMPTIONS

1. **`ahead: true` → `position=0`** — orchestrator-frozen (the spec's
   "ahead of the current next item" wording vs `position=0`: kept 0; the
   live queue retains its already-played prefix (current item sat at
   position 29), so `position=0` = head of the queue LIST, verified
   landing 0..N-1 both fake and on-device. R-24's play-next-from-a-queue-
   row (position after current) is a different issue, untouched).
2. **Add to Up Next pins `position = current queue length`** (from the
   controller's WS-live list). With the server's shuffle mode on, an
   omitted position is a RANDOM-slot insert (live-proven), so the tail
   contract needs the pin; a concurrent-session add between the    controller's last refetch and the POST could land a few slots early —
   accepted
   best-effort, the WS `queue` event re-syncs the UI immediately.
3. **Shuffle-play = client-side pre-shuffle** (the adjudicated
   if-no-server-param path): the add-time `shuffle` param mutates the
   GLOBAL shuffle mode (live-verified flip + restore) → unusable under R-19.
   The pre-shuffle plays the set in random order and leaves the flag
   untouched whatever its state (on this server the flag is `true`, so the
   effective order is server-randomized on top — still a shuffled play,
   still no mutation).
4. **ArtistAlbumsScreen Shuffle shuffles the ALBUM URIs** (block shuffle)
   — expanding every album's tracks would be an N+1 fetch the issue does
   not ask for; Play All / Play Next / Add ride `library:artist:<id>`.
5. **Playlist/Album Play All / Play Next / Add ride the CONTAINER uri**
   (`library:playlist:N`, `library:album:ID`) — single-call server
   expansion preserves track order and matches the capture notes
   (`18-playlist-detail/notes.md`: `uris=playlist:…`); only Shuffle
   expands to per-track URIs (one `limit=-1` fetch).
6. **Empty rule = whole-button disabled while loading/empty** (the
   adjudication allowed hidden or disabled; disabled keeps a stable app
   bar for a11y).
7. `limit=-1` for the expansion fetch (live-verified unbounded on both
   endpoints) — a `total`-respecting page loop was not needed.

## REVIEW-NOTE (for the PR body)

The two "suspicious simplifications" a reviewer will eye in
`owntone_api.dart` are load-bearing and mutation-checked by the live
findings above: dropping `playback=add` is not equivalent to sending it
(omission + shuffle-on ⇒ random insert), and "restoring" the add-time
`shuffle` param would silently mutate the server-wide shuffle flag R-19
forbids. Do not tidy them away.
