**Controller** (`lib/src/queue/queue_controller.dart`):
- `removeItem(item)` — `DELETE /api/queue/items/{id}` (docs/API.md:95,
  204 — semantics confirmed via docs-mcp official json-api docs
  2026-11-20) through `_action` VERBATIM: optimistic splice (id-keyed,
  so the hide-cut can never index-shift the wrong row out), rollback +
  typed `_describeActionError` snackbar on failure ("Remove failed —
  server answered HTTP 500."), trailing post-commit `_refresh`
  (unit-011 single-flight — same warning comments as `moveItem`, NO
  second refresh path).
- `playNext(item, {required position})` — `POST /api/queue/items/add`
  with `uris` = the row's own uri and `position = current + 1`, **no
  `clear`**, `playback=add`. **Insert-COPY is the CHOSEN semantics**
  (orchestrator-frozen, recorded in the code comment): the original row
  stays and the track plays twice — ReTune's safe default. Move
  semantics (remove+insert) NOT chosen: a queued row is the user's own
  ordering and a compound remove+insert can half-fail (item gone, copy
  not in). **No optimistic edit** (mirrors `addUris`): the WS `queue`
  event + `_action` trailing refresh land the list.
- `queuePlayNextPosition(queue, itemId)` — pure (next to
  `queueMoveNewPosition`, shares `indexOfNowPlaying` — one "current"
  definition for highlight, hide-cut and play-next):
  `indexOfNowPlaying + 1`; no current entry (stopped or an itemId the
  list does not hold) → **0** (head; minimal interpretation —
  ASSUMPTIONS).

## ASSUMPTIONS

1. **Play Next with NO current entry → `position=0`** (queue head):
   "play next" with nothing playing means next = first. Minimal
   interpretation (the issue only specifies `current+1`); pure-tested.
2. **Insert-COPY frozen** (orchestrator adjudication): copy semantics +
   decision recorded in the `playNext` code comment and this report.
3. **Device "tail rows" = the two LAST rows** (1394/1395) — far from
   the current index 491; never touched the current/now-playing row;
   no play/toggle request at any point.
4. **On-device row-tap skip-in-place was deliberately NOT exercised**:
   the #21 handler is `PUT /api/player/play?item_id=` — an endpoint the
   audio-safety rules classify as play-class (could transition into
   play); the non-regression contract is pinned by the widget test
   (body tap fires exactly the skip, opens no popup) plus the on-device
   observation that the accessory sits beside the body, not over it.
5. **Server-side DELETE of the NOW-PLAYING entry UNPROBED (deliberate)**
   — probing would mutate the live session's current row on a shared
   server (fixture-preservation rule). The rule is enforced client-side
   (no menu on that row — pinned by both harnesses). Same posture as
   #46's current-entry-move assumption.
6. **"Removing above the cut"** is honoured as: rows above the hide-cut
   are NOT renderable hence not removable via UI (no menu), and the
   id-keyed DELETE makes an index-shifted wrong-row removal
   structurally impossible — asserted both ways in the interplay test
   (no DELETE for the hidden id, hidden region intact after a below-cut
   remove).
7. **First-launch phone-permission dialog allowed** (the call-pause
   tracker's runtime permission; app behaves identically denied — not
   this issue's surface).
8. `build/night47/` holds the evidence artifacts (dumps, snapshots,
   digests, logcat probe) — git-ignored scratch, per the run config
   (repo `build/` dir; literal `/tmp` blocked for file tools).

## REVIEW-NOTE (for the PR body)

Load-bearing things a reviewer may "tidy": (1) `removeItem` must stay
ID-keyed — an index-splice would remove the WRONG row whenever the
hide-cut shifts between build and tap; (2) `playNext` rides `addUris`
without `clear` — routing it through `playUris` (or adding `clear`)
re-creates the #21 queue-replacing defect; (3) the insert-COPY choice
is deliberate (ReTune safe default, orchestrator-frozen — see
`playNext`'s doc comment); (4) the no-optimistic-edit on `playNext` is
the `addUris`/#41 contract — a local splice would double-render until
the trailing refresh lands; (5) do not re-add a second refresh path in
either action (unit-011).
