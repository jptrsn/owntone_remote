## SUMMARY

R-18 (D-09, `docs/retune-capture/14-speakers/`): outputs are now **one tap
from every browse screen**, matching ReTune's app-bar Speakers action instead
of living only behind now-playing's "Playing via" row
(`now_playing_screen.dart:329`). `BrowseScreenScaffold` already carried
`actions:` support (unit 005b), so the change is one shared widget —
`OutputsAppBarAction` in `browse_screen_scaffold.dart` (an `IconButton`,
tooltip + `semanticLabel` 'Outputs', `Icons.speaker` — ReTune's "Speakers" —
pushing the same `OutputsScreen` as now-playing) — wired at the two browse
call sites the issue names: `LibraryHomeScreen` (`browse_screens.dart`) and
`PagedBrowseScreen` (`paged_browse_screen.dart`, covering all eight paged
lists: playlists, playlist tracks, artists, artist albums, albums, album
tracks, genres, genre albums). It is deliberately NOT baked into the scaffold
itself: that would also give QueueScreen (which already carries two actions)
a third app-bar action — exactly the unit-004 360-px overflow situation R-18
warns about.

Tests: new `test/outputs_appbar_test.dart`, 4 cases, all citing R-18,
network-free via the existing fakes (`ScriptedAdapter` + `FakeWsChannel`):
library home and the Albums paged list each pumped at exactly **360×800**
(`tester.view.physicalSize`) assert no RenderFlex overflow
(`takeException isNull`), the icon present by tooltip AND by semantics label,
rows still render; tap-through from both screens asserts `OutputsScreen`
opens with the fake provider's output **names** (Alpha/Beta — the real
destination, not a stub route); back navigation returns to the browse list
with the action intact.

## ASSUMPTIONS

- **Scope = R-18's own enumeration**: library home + the paged browse
  (screens built on `PagedBrowseScreen`). `SearchScreen` and `QueueScreen`
  were NOT given the action: they are not "paged browse lists", and
  QueueScreen already carries two app-bar actions — adding a third would
  reproduce the unit-004 360-px overflow the requirement explicitly warns
  about. The issue's frozen "Where" lists exactly the three files touched.
- Icon: `Icons.speaker` chosen as the own-app rendering of ReTune's
  **Speakers** action (D-09) — clean non-solid glyph (passes the
  `glyph_hygiene_test` family ban, which covers only `Icons.shuffle_on*`);
  tooltip + `semanticLabel` 'Outputs' give the widget test (and TalkBack)
  the semantics label the acceptance names.
- Pressable while offline (queue hide-toggle precedent): the action touches
  nothing on the server; `OutputsScreen` renders the offline banner +
  waiting state itself. Disabling it with the connection would regress the
  "one tap from any browse screen" acceptance.
- Device pass opened the outputs sheet read-only while the server was
  paused — no output toggles were needed for the behaviour claim (the
  claim is *reachability*, not selection), so none were made.
- Evidence channel: agent-lens / widget-inspector trees and flutter_driver
  unavailable after honest attempts → uiautomator + screencap + console
  (explicitly allowed fallback; channel stated above). Screencaps live
  under git-ignored `build/night-scratch/` (image reads are blocked anyway
  — the model has no image input — so numbers are quoted from uiautomator
  bounds + the console grep).
- Connect screen on a fresh install: port field was empty (hint 3689);
  typed `3689` explicitly before Connect (mirrors unit #43's harness step).

## Corrections — 2026-11-21 (independent review of merged PR #52 + evidence audit)
- The "wm density 300 … 1080 px ÷ 300 dpi = exactly 360 logical px" line is arithmetically WRONG: `wm density N` sets densityDpi, logical px = physical × 160/N → 1080 × 160/300 = **576 dp**. The on-device row measured a 576-dp viewport, not 360. The exact-360-logical-px constraint remains genuinely pinned by `test/outputs_appbar_test.dart` (physicalSize 360×800 **@ dpr 1.0**) — the deterministic test, not the device row.
- "verified 05:04Z local start" fits no coherent timeline (artifact mtimes 23:33–23:36 local, commit 00:19 local).
- PR-body wording "4 R-18 widget tests at 360x800" overstates: only the presence/no-overflow tests set the 360×800 viewport (the tap-through tests run at the default viewport).
