## SUMMARY

Material 3 `Drawer` behind a hamburger on **every main screen**:
Now Playing's Scaffold, every `BrowseScreenScaffold` screen (new `drawer`
param mirroring `actions:`, defaulting to a plain `AppDrawer()` so the
hamburger can never be forgotten — Search and the detail views included),
and the standalone Outputs/Settings Scaffolds. New `lib/src/ui/app_drawer.dart`:

- Header **`Connected To — My Music on hp-server`** — the `/api/config`
  display name (`library_name`), surfaced via a new
  `ConnectionController.serverName` (same lifecycle as `serverVersion`:
  set on connect, kept while offline, cleared on disconnect). The
  `OwnTone <version>` label moved from the now-playing app bar into the
  header subtitle (see GATES/commit for why).
- Sections **Playing** (Now Playing · Queue), **Library** (Library home +
  direct deep links Playlists/Artists/Albums/**Songs**(#38/merged)/Genres),
  **Settings** (Settings · Outputs) — M3 section labels (`labelLarge`,
  primary).
- Navigation: `showDrawerDestination` next to `showNowPlaying` in
  `root_screen.dart` — `popUntil(isFirst)` **then** push (the frozen
  contract; Now Playing destination = plain `showNowPlaying`). A
  NavigatorObserver-based regression test asserts **stack depth 2**
  ([root, queue]) after Queue-from-two-deep, plus the back-tap-sequence
  proof (one back from Queue = root).
- Selected destination: `ListTile(selected:)` — carries
  `Semantics(selected:)` (verified through the Android a11y bridge:
  uiautomator `selected="true"` only on the hosting screen's row).
- Offline: drawer opens (header survives — identity is not re-fetched);
  server-touching destinations (`Queue`, all Library items, `Outputs`)
  inert via ListTile's explicit `enabled` flag (a null `onTap` does **not**
  disable ListTile semantics — caught by the test); Now Playing (plain
  pop) + Settings (offline escape hatch) stay live.
- ReTune's missing-drawer-on-UpNext quirk NOT copied (spec;
  `docs/retune-capture/23-playing-audit/notes.md` — ours opens everywhere).
- Interaction with #40's `OutputsAppBarAction`: untouched — the app-bar
  Outputs action and the drawer's Outputs destination coexist (verified
  on-device on Library home: hamburger + Back + Outputs action + title
  all render at 411 dp, no overflow).

Two implementation traps the drawer walked into and out of (both pinned
in code comments + tests):

1. **AppBar leading**: with a Scaffold drawer, AppBar's auto-leading shows
   the DrawerButton **instead of** the BackButton (app_bar.dart's
   `if (hasDrawer)` branch) — pushed screens would have lost their back
   arrow entirely. `drawerAwareLeading` + `drawerAwareLeadingWidth` (the
   pair — AppBar pins the leading slot to 56 px, the two-button Row
   overflows it by exactly 40 px otherwise, mutation-observed).
2. **360-px app-bar budget**: with the hamburger's 56-px leading slot
   taken, the now-playing app bar's trailing (version label + sync label +
   settings + overflow menu) overflowed by 65 px at 360 logical px — and
   the overflowing actions painted over the hamburger and swallowed its
   taps. The version label moved to the drawer header (the About screen
   still shows it; nothing else pins it). Mutation-verified by the
   takeException checks in `test/app_drawer_test.dart`.

## ASSUMPTIONS

1. **Server display name = `/api/config` `library_name`** — the only
   display-name field the endpoint serves (live: `My Music on hp-server`);
   `ConnectionController.serverName` mirrors the existing
   `serverVersion` pattern (kept while offline, cleared on disconnect);
   the header falls back to `config.host` then `server` pre-first-connect.
2. **"server-touching destinations inert" adjudicated** as: Queue + all
   Library destinations + **the drawer's Outputs row** are disabled while
   offline (the frozen repro says "offline → items inert"; the NP
   `Playing via`/Queue entry rows are the "existing enabled contract").
   **Now Playing and Settings stay live** (neither touches the server to
   open; Settings is the offline server-entry escape hatch). The
   **app-bar** Outputs action keeps its separate #40/R-18
   pressable-while-offline contract (frozen adjudication of a different
   entry point) — not unified; both documented in `app_drawer.dart`.
3. The hamburger leads with DrawerButton-then-BackButton on pushed
   screens (Material nav-icon position); root routes show the hamburger
   alone (AppBar default behaviour).
4. Moving the `OwnTone <version>` label from the NP app bar to the drawer
   header was the minimal change that keeps the 360-px fit once the
   hamburger takes its leading slot (required by the spec's "hamburger on
   every main screen"); the version remains visible in the drawer header
   and on About. No test pinned the app-bar copy.
5. Hamburger is `DrawerButton` (auto-injected with a drawer / explicit via
   `drawerAwareLeading`) — tooltip `Open navigation menu`; tests/device
   assert it per screen as the spec's "hamburger found" contract.
6. The About screen (reachable only from Settings, a secondary screen)
   stays without a drawer — the spec enumerates "Now Playing + every
   BrowseScreenScaffold screen + outputs/settings".
7. Emulator viewport is 411-logical-px-ish (1080 px @ 2.625 dpr,
   pixel_6 profile); the 360-px constraint is pinned by the widget tests
   (widget-test viewport 360×800 — the binding default of 266 logical px
   is not a supported surface).
