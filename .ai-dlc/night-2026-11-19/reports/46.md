## SUMMARY

**UI** (`lib/src/ui/queue_screen.dart`): `_QueueList` renders a
`ReorderableListView.builder` (`buildDefaultDragHandles: false`); each
draggable row carries a `ReorderableDelayedDragStartListener` drag handle
(`Icons.drag_handle`, row right edge) — the DELAYED variant is the load-
bearing choice: in Flutter 3.47.9 the plain listener starts the drag
IMMEDIATELY on pointer-down (would steal row taps/scrolls); the delayed
one waits out the long-press timeout = ReTune's "tap and hold to drag"
(16-up-next). Commit fires on drop via **`onReorderItem`** (the
deprecated `onReorder` stays at zero issues — do not reintroduce it).
Flutter 3.47.9 has no `separatorBuilder` on `ReorderableListView` — the
8 px row gap is baked in as per-item bottom padding (geometry-equivalent
to the old `ListView.separated`).

- **Hide-played interaction — CHOSEN: map the display drop through the
  cut (option (a) of R-23), NOT disable-drag-while-hidden.** `queueMoveNewPosition`
  (pure, next to `visibleQueue`, `queue_controller.dart`) converts the
  drop's display indices to the absolute `new_position`; it shares ONE
  cut definition with `visibleQueue` via `_hideCutStart` (a mapping that
  disagreed with the rendered cut would move the WRONG entry). Covered
  by unit tests incl. the cut cases + the widget test dropping inside a
  hide-cut window (display 0 → `new_position=1`, never 0). **State this
  choice in the PR body.**
- **Now-playing row inert**: it gets NO drag handle at all (no listener ⇒
  no drag, no request — verified on-device, OBSERVED). The server-side
  behaviour of moving the current entry is deliberately **UNPROBED**
  (shared fixture — the rule is enforced client-side; see ASSUMPTIONS).
- **Mid-drag WS `queue` event**: the list FREEZES while dragging
  (identical cached list widget + frozen items closure — a rebuild under
  the live overlay trips Flutter 3.47.9's duplicate-`GlobalKey`
  assertion; reproduced). Unfreeze runs on `onReorderItem`'s NEXT frame
  (the framework calls `onReorderItem` BEFORE its own `_dragReset` —
  unfreezing in that same frame collides with the still-mounted proxy;
  also reproduced) with a 500 ms timer covering same-place drops. The
  drag keeps its local order; the `_action` trailing refresh reconciles
  — documented by the mid-drag widget test (frozen mid-drag + exactly
  one PUT + final order == server order).
- **Semantics**: handle label `Reorder <title>` (ReTune's drag is
  a11y-invisible — 23-playing-audit — R-23 says do better). Visible in
  the live uiautomator content-desc (OBSERVED).

**Controller** (`QueueController.moveItem(item, newIndex)` —
`queue_controller.dart`): follows `_action` VERBATIM — optimistic
remove + insert-at-N (mirrors the server's MOVE semantics, not a swap),
failure restores the pre-action list + typed `_describeActionError`
snackbar ("Move failed — server answered HTTP 500."), trailing
post-commit `_refresh` (unit-011 single-flight). **No second refresh
path** — pinned by the controller test (`fired == [PUT, GET /api/queue]`

**API** (`OwntoneApi.moveQueueItem`): `PUT /api/queue/items/{id}

(`PUT /api/queue/items/196175?new_position=2` — ScriptedAdapter request

## ASSUMPTIONS

1. **Now-playing-move server behaviour UNPROBED (deliberate)** — probing
   it means moving the live queue's current entry on a shared server
   (fixture-preservation rule; another session is active). The rule is
   enforced client-side (no handle ⇒ inert; pinned by both harnesses).
   If OwnTone does accept `new_position` on the current entry, our UI
   simply never sends it. Rationale carried here per the adjudication.
2. **Hide-played: map-through-cut chosen** over disable-drag (the
   simpler CORRECT option — the pure map is 4 lines + tests; disabling
   would strand the feature for a state users toggle freely). The honest
   corner this admits: under hide-ON, dropping a row above the current
   row lands it at the anchor boundary and it then joins the HIDDEN
   region (the row vanishes from the window — server-consistent: it is
   "played territory"); the equivalence test pins window == server truth
   rather than ghost-slot preservation. State in the PR body.
3. **`onReorderItem` (adjusted) indices are the drop contract** —
   `queueMoveNewPosition` deliberately does NOT re-decrement; documented
   and mutation-motivated in code + tests (the old `onReorder`
   adjustment double-shifts downward drags).
4. Mid-drag WS event with the hide-cut ON could map a drop against a
   shifted anchor (the cut is re-derived from the live list at drop) —
   the trailing refresh reconciles; covered directionally by the
   mid-drag test (hide OFF there — hide-ON+mid-drag-events is a
   double-exotic combo the post-commit refresh still settles).
5. System-cancelled drags (pointer takeover mid-gesture) can leave the
   list frozen until the next drag/revisit (Flutter fires neither
   callback there) — documented limitation in code; not reachable via
   `input` injection.
6. The device drag targeted the head rows (abs 1↔3) — visually verified
   via content-desc geometry; the current row (abs 491) reached via the
   app's own hide-cut anchor instead of 33 blind flings (deterministic
   and it doubles as the cut's on-device proof).
7. `build/night46/` holds the evidence artifacts (dumps, snapshots,
   digests) — git-ignored scratch, per the run config (repo `build/`
   dir; literal `/tmp` blocked for file tools).
