**Port cross-check: SRV port 3689 == the JSON API port** answering
`GET /api/config` (`version 29.3`, `websocket_port 3688`, `library_name
"My Music on hp-server"` — the library_name IS the mDNS instance name).
So the app codes against what the server ACTUALLY advertises:
**browse `_http._tcp`, keep TXT-fingerprinted hits** (marker keys `ffid` /
`mtd-version` / `owntone-version`, key-position match). The DAAP-surface
advertisements (`_dacp._tcp`/`_daap._tcp`) are never browsed (AGENTS §5).

**Plugin (PR-body justification):** `multicast_dns 0.3.3+1` — pub.dev
verified publisher **flutter.dev** (repo flutter/core-packages), published
~5 months ago (active), **BSD-3-Clause, pure Dart, zero native deps**
(single `meta` dependency), 2.99M downloads. Alternatives considered:
`mdns_query` (the issue's suggestion) — **does not exist on pub.dev**
(page 404, API `NoSuchKey`) — recorded as unavailable, not chosen blindly;
platform-NSD plugin wrappers (`mdns_plugin`/`nsd` family) — native Android
deps + unmaintained → rejected; `network_info_plus` (issue mention) is a
Wi-Fi-info plugin, not an mDNS client — not applicable. Android permission
verification: **no new permission declared.** `INTERNET` (already present)
covers the transport because every query sets the **QU (unicast-response)
bit** — responses come back unicast to the app's ephemeral socket.
Android docs (WifiManager.MulticastLock, fetched 2026-11-20): the
MulticastLock gated by `CHANGE_WIFI_MULTICAST_STATE` is only needed to
"receive packets addressed to multicast addresses" — "Normally the Wifi
stack filters out packets not explicitly addressed to this device" — i.e.
it gates PASSIVE group-addressed listening, not query→unicast-answer
discovery. Confirmed: not needed for queries (Android NSD itself requires
no permissions for discovery).

**UI (`lib/src/ui/settings_screen.dart`)** — Scan is a **side panel** below
the manual form (never beside/over it): `OutlinedButton`
`server-scan-button` → own states: loading ("Searching the local network…"
+ spinner), results (`ListTile` per hit: name + `host:port`, key
`scan-hit-N`), empty ("No OwnTone server found on this network. **You can
still enter the address manually.**"), error/timeout (server-panel
`scan-error` + `scan-retry`), plus a ceiling `kScanTimeout = 12 s` on the
source future so the PANEL always resolves even if the backend hangs. The
manual host/port fields are ordinary `TextFormField`s outside the panel —
widget tests assert they are editable during a scan and functional after a
scan failure/timeout. **One-tap hit = `_useHit`: sets the two field
controllers then calls the EXISTING `_saveAndConnect()`** — same persist,
same `ConnectionController.connectTo` validation (R-01), zero
discovery-specific connect path.

**Discovery layer (`lib/src/discovery/`)** — `discovered_server.dart`
(value: name/host/port + `config` getter), `discovery_source.dart`
(abstract `DiscoverySource` + `DiscoveryException` — fake-injectable
contract), `mdns_discovery.dart` (`MdnsOwnToneDiscovery`: PTR browse →
parallel per-instance SRV/TXT → TXT filter → A-record resolve →
sorted/deduped hits; pure `isOwnToneTxt`/`ownToneInstanceName` helpers
unit-tested).

**Three engineering findings (measured, not guessed) — load-bearing:**
1. **Trailing-dot poison:** `LookupResolver.responseMatches` only
   normalizes request names ending exactly in `local`; the browse domain
   MUST be `_http._tcp.local` (no trailing dot) or the browse silently
   finds nothing (measured: 0 hits vs 10 with the dot stripped).
2. **`SO_REUSEPORT` starvation on the host:** `adb` (3 sockets) and Google
   Chrome (12 sockets) co-bind UDP 5353; multicast flows are distributed
   across co-bound sockets — the identical browse returned **13, then 9,
   then 0** answers across runs. Transport therefore binds an **ephemeral
   UDP port** (never 5353) and sends **QU** queries; responders (verified:
   the OwnTone/Avahi server, wire-dumped) answer unicast — deterministic.
3. **TXT newline-join:** the decoder concatenates a multi-string TXT RDATA
   with `writeln` (wire-verified), so the marker-key separator set includes
   `\n` (with space-only matching the real server would be REJECTED).

## ASSUMPTIONS

1. **Fingerprint = TXT marker keys `ffid`/`mtd-version`/`owntone-version`**
   (key position, case-insensitive, separators incl. `\n`/space/`;`).
   Chosen from the measured advertisement; `owntone-version` is accepted
   forward-compat. A malicious LAN device could spoof the markers — scan
   hits only pre-fill a form the user still connects through R-01 (which
   does the real verification: `/api/config` must answer); no trust is
   granted at discovery time.
2. **QU unicast replies everywhere** (browse/SRV/TXT/A) + ephemeral source
   port — see finding 2; the host's `adb`/Chrome 5353 co-binds make the
   5353 multicast listen unreliable, and the real server demonstrably
   answers QU (wire-dumped 323 B full PTR+SRV+TXT+A response).
   Side effect (honest): a responder that (mis)answers QU-only-ignoring
   devices would be missed; measured 12/13 LAN `_http._tcp` devices
   answered QU unicast — the OwnTone server among them.
3. **`pubspec.lock` stays gitignored** (repo convention; the run note
   expected "commit both" — repo rule wins, `git check-ignore` verified).
4. **Server was `play` (foreign session) during the device phase** — left
   untouched (pausing it would mutate the other session's playback;
   no device step of this unit could start audio).
5. **Device mDNS success is an emulator-NAT artifact possibility** — the
   google_apis image may proxy `.local`/mDNS via 10.0.2.3; recorded
   honestly; the morning Pixel-6 row carries the real-hardware verdict.
6. **Forced-degradation method** = own-AVD `iptables` drop of sport-5353
   (own AVD only, root available, removed and verified) — a device-local
   filter, no server/other-device impact.
7. The one existing-test edit (`settings_screen_test` ensureVisible) is
   layout-adaptation caused by this unit's row, using the test file's own
   documented pattern — not a scope widening.
