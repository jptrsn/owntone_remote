# Light/dark theme switcher — user choice of Light, Dark, or Follow system

(Canonical: https://github.com/jptrsn/owntone_remote/issues/43. Frozen copy for the 2026-11-19 overnight run.)

## Change
The app renders the light Material 3 scheme only: `MaterialApp` sets a single
`theme` (seed `0xFF7C5CBF`) with no `darkTheme` and no `themeMode`
(`lib/main.dart:153`), so a system-dark phone still gets a white app. The
user asked for a theme preference: **Light · Dark · Follow system**.

## Expected
Settings (the existing screen, next to the rocker step) gains a three-way
theme picker — `Light` / `Dark` / `System`:

- `Light`/`Dark` force the scheme; `System` (the default) follows
  `platformBrightness`, including live while the app is open (a system
  toggle mid-session re-skins the app with no restart).
- The dark scheme is `ColorScheme.fromSeed` with the **same seed**
  (`0xFF7C5CBF`, `brightness: dark`) — no bespoke palette in v1.
- The choice persists across restarts (same `SettingsStore` pattern as
  `rockerStep`: read-validate fallback so a corrupt/legacy value →
  `system`), and applies on the next screen without an app restart.
- No hardcoded colors: the two `Colors.grey` placeholders in
  `now_playing_screen.dart:765,770` become scheme-derived (e.g.
  `onSurfaceVariant`) so they stay legible on dark.
- Behavior change to call out: once `darkTheme` exists, `System` (default)
  will actually follow the system — users on a dark phone will see the app
  flip. Accepted (that's the point of the issue).

## Where
`lib/src/settings/settings_store.dart` (new key, e.g. `theme.mode`, stored
as a string, validated on read); a tiny `ChangeNotifier` for the preference
(`SettingsStore` is not listenable — `MaterialApp.themeMode` needs a rebuild
on change); `OwntoneRemoteApp` in `lib/main.dart` (add `darkTheme`, wire
`themeMode`); `lib/src/ui/settings_screen.dart` (`SegmentedButton` or
equivalent M3 control with `ValueKey`s, matching the rocker-step row's
pattern).

## Requirements
New requirement, proposed **R-21** (numbering at the maintainer's
discretion — a parallel session may claim it): theme preference with the
acceptance below; add to `docs/REQUIREMENTS.md`. Not a ReTune diff-list row
— direct user request 2026-11-19.

**Acceptance:**

- three modes render the correct brightness; default is `System`;
- selection survives app kill/relaunch;
- `System` follows a platform brightness change while running;
- corrupt persisted value degrades to `System`, never a crash;
- dark scheme derives from the existing seed.

## Repro / verification
Widget tests (no network, `SharedPreferences.setMockInitialValues`) derived
from the acceptance list: each stored mode → `Theme.of(context).brightness`
correct; tapping the picker flips brightness without restart; `System`
follows `tester.platformDispatcher` brightness change; garbage value →
system. Gates green (`analyze` / `format` / `test --exclude-tags live` /
`build apk --debug`). On-device check on the Pixel 6 (system dark toggle,
relaunch persistence) with evidence in the unit.
