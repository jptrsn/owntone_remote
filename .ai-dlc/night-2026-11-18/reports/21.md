## SUMMARY

Tapping a row in the Queue screen no longer clears the queue. The tap
handler (`queue_screen.dart` → `QueueController.playUris`) was firing the
browse/search play ceremony — `POST /api/queue/items/add?uris=…&clear=true
&playback=start` — on an already-queued item: the `clear=true` wiped the
user's whole queue down to the tapped track.

**The fix uses the web UI's own mechanism, read from the served reference
oracle** (AGENTS trap #3 honoured): the webplayer JS at
`http://192.168.1.13:3689/assets/index.js` (539 KB, `ListItemQueueItem`,
byte offset ~506028) renders every queue row with
`onClick: n` where `n = () => IS.play({item_id: item.id})`, and `IS.play
(e)` is `PUT ./api/player/play` with `params: e` (offset ~372785). The web
UI's in-place queue-skip is therefore **`PUT /api/player/play?item_id=<queue
entry id>`** — one call, queue content untouched, the entry becomes the
current track. The orchestrator-plan parameter `PUT
/api/queue/items/{id}?new_position=N` is the **drag-reorder** endpoint (same
JS: `zS.move(...)` fires only from the drag-drop handlers) and does NOT
change the current track — the code read, not the plan's guess, is the
authority (plan itself deferred: "trust the code you read, not the parameter
name here"). Corroboration: the official json-api docs don't even list the
`item_id` parameter — the served JS is the only oracle for it.

- `lib/src/api/owntone_api.dart` — `skipToQueueItem(entryId)` → `PUT
  /api/player/play` with query `item_id`.
- `lib/src/queue/queue_controller.dart` — `skipToQueueItem(item)` on the
  standard `_action` (typed error + trailing post-commit refetch, no
  optimistic edit: the item-change fires `player`+`queue` WS events that
  drive the UI). `playUris` stays untouched for browse/search (replace IS
  correct there).
- `lib/src/ui/queue_screen.dart` — row tap → `onSkip` → `skipToQueueItem`;
  the add-with-clear path is gone from the screen.
- Docs: `API.md` player/play row + `REQUIREMENTS.md` R-11 tap bullet +
  `SCREENS.md` queue Actions table (precedent: #19 updated R-09 likewise).

## ASSUMPTIONS

1. **"R-05 area" in the issue's fix-unit note → R-11 (Queue)** in
   `docs/REQUIREMENTS.md` (R-05 is Playback modes) — same misnumbering
   precedent as #19/#23/#24. Tests cite R-11.
2. **The skip endpoint is `PUT /api/player/play?item_id=<entry id>`, not the
   plan's `PUT /api/queue/items/{id}?new_position=N`** — adjudicated from the
   served webplayer JS (the designated oracle): the row click calls
   `IS.play({item_id})`; `new_position` fires only from drag-drop. The task
   text's "must issue NO play/toggle/playback=start call" is honoured in its
   evident intent — no queue-replacing add, no bare transport call; the
   handler's single request carries the `item_id` selector (that IS the web
   UI's skip mechanism; a new_position implementation would move position
   and leave the current track unchanged — failing the issue's own expected
   behaviour).
3. **Shared-server mutation window declined on snapshot drift** (queue 1432
   ≠ 0, foreign session): the authorized restore path was destructive in the
   drifted state and `item_id` is not restorable — refused per AGENTS rules
   1+4 rather than adapted. Fixture + CI tests carry the evidence; a
   supervised window with the user present is the clean path for the
   live-server tap-through.
4. **Tapping the now-playing row still fires the skip call** (no guard) —
   the web UI's handler has none; parity kept; harmless (re-selects the
   current entry; while paused it resumes, as the web UI does).
5. **`item_id` on the player is the queue-ENTRY id** (live-verified
   2026-10-23, unchanged): the skip keys on `QueueItem.id`, the same value
   the highlight already matches on — pinned by the widget test (196176 ≠
   track_id 1193).
6. **The fixture's WS server stands in for the real server's event push** —
   it sends `{"notify":["player","queue"]}` on skip exactly like OwnTone
   does (unit #23 pattern); the app's marker movement was driven by real
   WS-event handling, not a harness poke.
