## SUMMARY

Deselecting an active output always opened the unit-004 live-audio-redirect
confirm (`outputs_screen.dart` ~line 69 → `_withPlayingGuard` wrapped EVERY
checkbox tap), even when other outputs stayed selected and audio continued
uninterrupted.

**The fix (OwnTone web-UI parity, oracle-read):** the served webplayer
(`http://192.168.1.13:3689/assets/index.js`, `ControlOutputVolume`) fires
`XS.update(output.id, {selected: !output.selected})` with **no confirm
anywhere** (grep `confirm` over the 539 KB bundle: 0 hits) — so a deselect
that leaves outputs selected must be fully silent. The last-selected
deselect keeps a confirm of the app's own (the issue's guardrail):

- `lib/src/outputs/outputs_controller.dart` — new pure static
  `emptiesSelection(outputs, id)`: true iff `id` is the ONLY selected
  output. The UI routes on this: multi-deselect → silent `toggle`;
  last-deselect → confirm; enable (PIN or not) → the unchanged unit-004
  playing guard (minimal scope — the issue's defect is deselect-only).
- `lib/src/ui/outputs_screen.dart` — `_onCheckbox` three-way split;
  `_lastDeselectFlow`: confirm (in ANY player state — a stale cached
  "pause" is exactly what a playing server looks like) → `toggle` →
  on success read the player slice FRESH (`player.refreshState()`,
  unit-004 cache contract) → if `isPlaying`, `player.stop()`
  (`PUT /api/player/stop`, not pause: a playing server with zero outputs
  burns the queue emitting nothing; pause would keep advancing it).
  Failed toggle (optimistic rollback) ⇒ no stop.
- Docs: `REQUIREMENTS.md` R-09 acceptance bullet + `SCREENS.md` Outputs
  interaction-design bullets (precedent: #19/#21 updated docs likewise).

## ASSUMPTIONS

1. **"R-07 area" in the issue's fix-unit note → R-09 (Outputs / speakers)**
   — `docs/REQUIREMENTS.md`: R-07 is the persistent notification, outputs
   live at R-09; same misnumbering precedent as #19/#21/#23/#24. Tests
   cite R-09.
2. **Enable-while-playing keeps the unit-004 guard** (dialog + fresh read):
   the issue's defect and Expected list speak only of DESELECTS; removing
   the enable guard would widen scope (user decision 2026-10-22 stands for
   enabling, which does newly receive live audio).
3. **The last-output confirm shows in ANY player state** (incl. paused):
   the spec's test (d) ("last-deselect while PAUSED → confirm → no stop")
   requires it, and a stale cached "pause" is exactly what a playing
   server looks like — a state-gated confirm could be skipped by the very
   race the guard exists for.
4. **Stop fires only after a SUCCEEDED toggle and a FRESH play read**:
   a failed toggle rolls the selection back (nothing emptied ⇒ no stop);
   `player.refreshState()` (unit-004 contract) decides, pinned by test
   (e).
5. **Dialog wording is ours** (title 'No outputs left selected', content
   naming the zero-output consequence, Cancel/Continue): the web UI has no
   such dialog to copy (0 `confirm` in the bundle); the buttons mirror the
   existing guard's Cancel/Continue.
6. **`/tmp` denied by the harness** → scratch in `.night/20/` (gitignored,
   removed before returning), per the run-instruction fallback.
7. **Snapshot honored, not overwritten**: kickoff state matched the ledger
   10:45Z snapshot exactly (no foreign drift this session), so
   byte-identical restore to the SNAPSHOT was the restore target and was
   verified by sha.

  - **M3** `pause()` instead of `stop()` → 'last deselect while PLAYING'

    test fails.
  - **M6** `emptiesSelection` constant `false` → all four last-deselect
    widget tests + the controller pin fail; multi-deselect stays green.
