## SUMMARY

Tapping a search result that **initiates playback** now also switches the
active screen to the Now Playing view instead of leaving the user staring at
the results. The app has no tab bar: `RootScreen` renders `NowPlayingScreen`
as the root route and every listen screen (Library/Search, Queue, Outputs) is
pushed above it — so the "tab/nav switch" is one helper:

- `lib/src/ui/root_screen.dart` — new `showNowPlaying(context)`:
  `Navigator.popUntil((route) => route.isFirst)` (the documented meaning of
  "switch to Now Playing" for this navigation shape; a `push` would stack a
  duplicate now-playing screen and is called out in the doc comment).
- `lib/src/ui/search_screen.dart` — one shared `play(uris)` closure used by
  **every** group's play handler (tracks/artists/albums/playlists): fires
  `QueueController.playUris` (unchanged `clear=true&playback=start` call) and
  calls `showNowPlaying(context)`. Previously all four handlers fired the
  queue-add with no navigation.

Browse-screen taps do **not** navigate today (checked every `onPlay` in
`browse_screens.dart`/`queue_screen.dart` — they are bare `playUris`), so
there was no browse-side pattern to mirror; the helper is the new mechanism,
deliberately placed in `root_screen.dart` where the spec's "Where" points.

Tests (R-ID cited, in-repo fakes — `ScriptedAdapter`/`FakeWsChannel`):
`test/search_screen_test.dart` group
`R-13 play navigates to Now Playing (issue #24)`:
1. **track play switches the active screen off the results** — pumps the app's
   real shape (now-playing stub as `home`, `SearchScreen` pushed through the
   navigator), types a query, taps a track row; asserts **both** the
   `POST /api/queue/items/add?…&clear=true&playback=start` (the tap initiated

   path that navigates).

   (tooltip) button fires its queue-add and switches.

## ASSUMPTIONS

1. **`R-08/search area` in the issue's fix-unit note maps to R-13 (Search)**
   in `docs/REQUIREMENTS.md` — there is no search content under R-08 (Call
   handling). Tests cite R-13.
2. **`showNowPlaying` = pop-to-root.** The spec names a "tab/nav switch
   mechanism" in `root_screen.dart`; the app has no tab bar — Now Playing is
   the root route and everything else is pushed. Popping to the first route
   is the only correct "switch to Now Playing" for that shape.
3. **Browse-screen taps do not navigate today** (verified: every `onPlay` in
   `browse_screens.dart`/`queue_screen.dart` is a bare `playUris`), so the
   spec's "mirror how browse-screen taps navigate, if they do" resolves to
   "they don't" — the helper is introduced at the search site only. Making
   the browse/queue play paths navigate would be widening beyond the issue
   (its Where names only the search play handler + the nav mechanism);
   recorded as a follow-up candidate instead.
4. **Device check runs entirely on the loopback fixture**, not the shared
   server (orchestrator adjudication): the tap sends `playback=start`, which
   on 192.168.1.13 would start audible playback — forbidden. The shared
   server stayed byte-identical (`item_progress_ms 38427` before/after).
5. **Collection-row play buttons navigate too** (artist/album/playlist), not
   just track rows: the defect is "a search tap that initiates playback
   leaves you on the results", and those buttons fire the identical
   `playback=start` queue-add; the track-row case (the spec's example) is
   the primary test. Row taps that only open detail screens stay put
   (pinned by test 2).
